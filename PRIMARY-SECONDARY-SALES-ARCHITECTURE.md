## Architecture evaluation

| Approach | Schema complexity | SFA compatibility | Pricing and units | Schemes | Reporting/security | Decision |
|---|---|---|---|---|---|---|
| A. Reuse `Product2`, `Order`, `OrderItem`, `Account`, and price books | Low to moderate; add channel configuration and transaction snapshots. | Highest: existing secondary-order and SFA pricing/order services use these records. | `PricebookEntry.UnitPrice` supports channel prices; channel and unit metadata identify the correct entry. | The live org already has scheme, scheme-product, and order-scheme objects and services; extend those. | One order history and existing account scoping; channel analytics can aggregate by `Order.Type`. | **Selected.** |
| B. Separate Primary and Secondary product records/configurations | High if separate products are created; moderate if represented by channel-specific price books. | Duplicate products risk breaking SFA product identity, inventory, and reporting. | Channel price books reuse the existing standard pricing mechanism without duplicating physical products. | Does not itself provide a scheme model. | Duplicated products complicate access, analytics, and auditability. | Reject separate product records; use the price-book portion of this approach within A. |
| C. Separate Primary and Secondary order objects or record types | High and duplicative; requires parallel lifecycle and integration paths. | Lowest: existing invoice and fulfillment paths expect standard `Order`/`OrderItem`. | Does not solve channel-specific prices or units. | Does not solve scheme configuration. | Splits reports, security, and history unnecessarily. | Reject. Reuse `Order.Type`; no new order object or record type. |

## Chosen model

1. Reuse standard `Order.Type` as the channel (`Primary Order` or `Secondary Order`). The existing `Secondary Order` value and `Outlet__c` relationship remain compatible with invoicing.
2. For Primary, the authenticated distributor is the `Order.AccountId`; no client-supplied distributor can override it. For Secondary, the same distributor is `Order.AccountId`, while `Order.Outlet__c` is an active outlet whose `Distributor__c` matches the session distributor.
3. Keep one `Product2` record per physical product. Require `Product2.SFA_Product__c = true` and use channel-tagged `Pricebook2` records and their `PricebookEntry.UnitPrice` for authoritative channel pricing. The product catalogue and order APIs return only entries from the matching active channel price book. Store each price entry's selling unit and conversion factor to the product's configured base unit.
4. Extend the live `Scheme__c` parent and `Scheme_Product__c` product rule rather than creating a second scheme model. Channel, product, active status, dates, units, and qualifying quantity determine eligibility. Apply the single highest-priority eligible rule; an equal-priority tie is a configuration error, with no stacking.
5. Snapshot the sales unit, conversion factor, paid/free quantities, list price, and tax on `OrderItem`. Use existing `Order_Scheme__c` records to link the applied scheme and rule and store applied/free quantities, discount, and status. Paid and free goods are separate order lines.
6. SFA submits Secondary orders to Salesforce; the DMS Secondary Orders page lists those shared records and does not create another Secondary order. Primary orders continue through the existing Salesforce approval process. Primary invoices and dispatches are company/warehouse operations in Salesforce and are read-only to distributors in the portal. An approved, Activated Primary Order is inbound: record received quantities through a GRN, which posts accepted goods to inventory. An Activated Secondary Order is outbound and needs no distributor approval: create its invoice directly, then validate/reserve stock from a selected distributor-owned warehouse if applicable. Dispatch confirmation consumes reserved quantities, or deducts available quantities when there is no reservation; invoice posting itself does not move stock.
7. Reuse the token-authenticated Apex REST pattern and existing React auth context/API module. The backend is authoritative for price, eligibility, scheme selection, totals, and account authorization.

## Added local configuration and snapshots

The implementation extends the existing standard records rather than creating channel-specific Products or Orders:

| Object | API name | Purpose |
|---|---|---|
| `Product2` | `QuantityUnitOfMeasure` (existing standard field) | Identifies the common product unit used by conversion factors. Existing `DMS_Tax_Rate__c` is reused. |
| `Pricebook2` | `Sales_Type__c` | Tags a DMS price book as Primary or Secondary; existing untagged SFA price books remain unchanged. Configure one active DMS price book per channel. |
| `PricebookEntry` | `Unit_of_Measure__c`, `Unit_Conversion_Factor__c` | Stores the channel-specific selling unit and number of base units per selling unit. `UnitPrice` remains the configured channel price. |
| `Order` | `DMS_Request_Key__c` | Unique external request key for safe order-submission retries. `Order.Type` remains the channel classification. |
| `OrderItem` | `Paid_Quantity__c`, `Free_Quantity__c`, `Unit_of_Measure__c`, `Unit_Conversion_Factor__c`, `DMS_List_Price__c`, `DMS_Tax_Rate__c`, `DMS_Tax_Amount__c` | Snapshots quantities, units, list price, and tax; scheme audit uses existing `Order_Scheme__c`. |
| `DMS_Invoice__c` | `Secondary_Order__c`, `Retailer__c`, `Warehouse__c`, existing status and totals | Reuse the existing required `Order` lookup (the field label is `Order`) for both channel types; the linked standard `Order.Type` distinguishes Primary and Secondary invoices. Primary invoice creation is company-owned in Salesforce; the distributor API returns existing linked records. |
| `DMS_Invoice_Line__c` | `Order_Line_Item__c`, product, quantity, price, discount, tax and total fields | Snapshot the server-validated order lines; the saved invoice response supplies the preview. |
| `Goods_Receipt_Note__c` | `DMS_Dispatch__c` (new) | Links a Primary Order receipt to the exact company-created dispatch being received. |
| `Goods_Receipt_Line_Item__c` | `DMS_Dispatch_Line__c` (new) | Links each receipt line to its exact dispatch line and `OrderItem`, preserving separate paid and free lines even when they share a product. |
| `Scheme__c` (existing) | `Sales_Type__c` (new) | Tags an existing scheme as Primary or Secondary. Existing `Scheme_Name__c`, `Scheme_Type__c`, status, active flag, and dates are reused. |
| `Scheme_Product__c` (existing) | `Minimum_Unit__c`, `Free_Unit__c`, `Priority__c` (new) | Adds units and priority to the existing product-specific quantity and discount rules. |
| `Order_Scheme__c` (existing) | No new fields | Reused for applied scheme/rule links, quantities, discounts, and status. |

Scheme unit quantities are converted through the product's base unit using active pricebook-entry unit factors. A scheme is eligible only if its minimum and free units have a consistent configured conversion for that product. It is then ranked by priority; a tie at the highest eligible priority is rejected. New orders are Draft; only the existing activation/fulfillment flow may advance them.

## Configuration and API contract

- Maintain one active `Pricebook2` tagged `Primary` and one tagged `Secondary`. Populate each eligible `PricebookEntry` with its channel price, selling unit, and positive conversion factor to the associated product's base unit.
- Ensure the standard `Order.Type` picklist accepts `Primary Order`; the existing source already uses `Secondary Order`. This must be checked in the target org because the local source does not contain standard-picklist metadata.
- Set the scheme parent to Active with a valid date range and channel; configure product rules with quantities, units, active status, and priority. Higher numeric priority wins. Existing SFA schemes without a channel are not implicitly assigned to a DMS channel.
- `GET /dms/v1/orders?view=catalog&type=Primary|Secondary` returns the authenticated distributor, authorized retailers, channel products, and currently active schemes.
- The same catalog response returns active warehouses owned by the authenticated distributor for invoice creation.
- `POST /dms/v1/orders` supports `action=preview` and `action=create`. Both actions recompute prices and scheme benefits server-side. Create requires a unique `requestKey`.
- `GET /dms/v1/orders?view=history&type=Primary|Secondary` returns that distributor's channel history in 100-order cursor pages. Pass the returned `nextCursor.createdAt` and `nextCursor.id` as `cursorCreatedAt` and `cursorId` to load the next page. `GET /dms/v1/orders?orderId=...` returns details only when the order belongs to the authenticated distributor.
- Order history includes the latest related invoice, dispatch and GRN summaries. Order details include every distributor-scoped dispatch and GRN with its recorded lines; the portal refreshes from Salesforce on entry and on explicit refresh.
- Primary receipts use `recordGoodsReceipt` with a `dispatchId` and a `dispatchLineId` on every receipt line. The API validates dispatch ownership, order and line identity, product and unit, and cumulative quantities; it does not infer a match from product names. Each approved receipt adds physical received and damaged quantities to the exact dispatch line, derives short quantity from dispatched minus physically received, and posts only accepted quantity to usable inventory. Receipt creation and these updates are atomic and idempotent.
- Approved legacy GRN lines without an explicit dispatch-line link are not guessed into a dispatch line; reconcile them before receiving additional quantities against the affected order line. The existing GRN endpoint remains the receipt transaction boundary; no competing trigger or Flow is added.
- `POST /dms/v1/inventory` supports `createWarehouse`, `updateWarehouse`, `receiveStock`, `recordGoodsReceipt`, `adjustStock`, and `transferStock`. Movement references are idempotent and each completed movement is recorded in `Inventory_Transaction__c`.
- `POST /dms/v1/orders` also supports `validateStock`, `reserveStock`, `releaseStockReservation`, and `reservationStatus`. Stock validation and reservation require an Activated Secondary Order and an active warehouse owned by the authenticated distributor; secondary orders do not require distributor approval. Primary Order receipts use the GRN workflow instead. Reservation requests require a unique idempotency key.
- `Inventory_Transaction__c.Transaction_Type__c` metadata preserves the six existing values and adds the active `Stock Transfer`, `Stock Reservation`, and `Stock Release` values; `Stock Adjustment` remains active. The API also checks active values and returns a configuration error rather than silently recording a different transaction type.
- `POST /dms/v1/invoicing` with `action=createInvoice` creates or retrieves a saved Draft invoice for an eligible Secondary order. Primary invoice creation through the distributor session is rejected; the distributor retrieves company-created primary invoices through the order and invoicing GET resources.
- Invoice posting remains a separate action and is rejected until the linked order is Activated. Creating or previewing a Draft invoice does not move stock. Eligible Secondary Orders become Activated after their lines are saved and can be invoiced directly without approval. Secondary invoices continue through the existing dispatch and stock transaction path; Primary dispatches are read-only to distributors, while Primary receipts continue through the existing GRN workflow.
- Secondary dispatches can be confirmed directly without an approval step. Dispatch confirmation revalidates the order reservation against the dispatch quantities and warehouse, then reduces reserved stock or available stock exactly once and records the corresponding inventory transactions. Invoice posting changes invoice status but does not move inventory.
- No separate `Ready for Invoicing` value is added: an eligible Secondary `Order.Status = Draft` is ready for invoicing, and invoice creation promotes it to `Activated`. The existing invoice status moves from Draft to Posted; dispatch records move from Draft to Dispatched, with delivery progress in `DMS_Dispatch__c.Delivery_Status__c`. Order activation is not a distributor approval.
- `GET /dms/v1/invoicing` returns the authenticated distributor's invoices with `amountPaid`, `balanceDue`, `paymentStatus`, and each invoice's `paymentReceipts`.
- `POST /dms/v1/invoicing` with `action=recordPayment` records a received payment against a Posted or Partially Credited invoice. Send `invoiceId`, positive `amount`, supported `paymentMethod` (`Bank Transfer`, `UPI`, `Cash`, `Cheque`, or `Other`), and a unique `requestKey`; `receiptDate`, `referenceNumber`, and `notes` are optional. The API creates `DMS_Payment_Receipt__c`, updates the invoice's paid/balance totals, prevents overpayment, and returns the receipt number and updated balance. Retrying the same request key and payment returns the existing receipt; reusing the key for different payment data is rejected. This records an already-received payment; it does not process a bank/card transaction.
- `POST /dms/v1/invoicing` with `action=downloadReceipt` returns an authenticated `application/pdf` attachment for a receipt owned by the distributor. `action=emailReceipt` sends that same generated PDF to the explicitly supplied `recipientEmail` using Salesforce email. The PDF is rendered by `DMSPaymentReceiptPdf`; Salesforce must have outbound email enabled to deliver email. Neither action creates a Salesforce file record.

## Inventory management and reservations

Warehouse create/update, receipts, adjustments, transfers, order reservations, reservation releases, and dispatch stock movements all use the existing warehouse, inventory-balance, and inventory-transaction records. No parallel inventory or reservation object is introduced. `Warehouse_Code__c` is an auto-number generated by Salesforce; `Inventory__c.Stock_Status__c` is formula-driven, so neither is written by the API. Distributor operations are scoped to the session distributor; company Primary operations use a separate Salesforce-authenticated API and require the `DMS_Company_Inventory_Access` custom permission. Both paths validate warehouse type and active status, lock affected records, and write audit transactions alongside balance changes. Transfers create paired transactions with a shared reference.

Reservations are ledger-derived from `Stock Reservation` and `Stock Release` transactions keyed to the order and idempotency reference. Reserving shifts quantity from available to reserved; releasing shifts it back. Invoice posting consumes the reservation by reducing reserved quantity and recording a release transaction in the same transaction as invoice posting. An order cannot be reserved while another active reservation exists, or released after an invoice is posted.

## Company warehouse Primary fulfillment

`Warehouse__c.Warehouse_Type__c` distinguishes `Company Warehouse` from `Distributor Warehouse`. A company warehouse must have no `Distributor__c` owner; distributor inventory, ordering, invoicing, dispatch, and GRN operations only accept distributor warehouses. `Inventory__c` remains the shared balance object, keyed operationally by product and warehouse, while APIs expose only the warehouse type they own.

The company-only `/services/apexrest/dms/company/v1/primary/*` resource supports company inventory and active company-warehouse reads plus Primary invoice/dispatch lifecycle actions. An approved and activated Primary Order can be invoiced against an active company warehouse. Posting the invoice does not change stock. Dispatch drafts are submitted to the existing `DMS_Dispatch__c.DMS_Dispatch_Approval` process; confirmation requires Salesforce approval, revalidates the invoice quantity and company stock under row locks, deducts `Inventory__c.Available_Quantity__c`, and records `Primary Order Sale` transactions. A dispatch retry verifies the prior transaction totals rather than deducting twice. Delivery updates do not change inventory. The distributor session endpoints remain unable to create Primary invoices, dispatches, or access company inventory.

Assign the `DMS_Company_Inventory_Access` permission set only to approved company operators; it grants API access, access to the company Apex REST class, and the custom permission checked by that resource. Before deployment, verify the existing org's warehouse-type picklist values and classify existing warehouse records; records with a blank or mismatched type are intentionally excluded from the corresponding inventory operations. This project does not deploy metadata or modify live Salesforce records.

## Local-source limitations and deployment gate

The checked-in Salesforce source omits part of the live org's schema and SFA Apex. The authorized `SFAOrg` was inspected for its `Order.Type` values and existing scheme/pricing services. Metadata additions must be limited to fields absent from that org; the local source is being aligned before deployment validation. No deployment success is implied by this design document.

The local source does not define scheme stacking, so the selected highest-priority rule was confirmed by the user. Equal-priority ties will be rejected to avoid nondeterministic pricing.

## Order approval workflow

Orders continue to use the standard `Order` object and `OrderItem` lines. Primary Orders retain the existing Salesforce `Approval.process` flow after server-side line validation. An authorized company operator creates and posts the Primary invoice through the company-only Apex REST resource when the order is approved; the distributor API does not create Primary invoices. Approval remains authoritative for Primary Orders, and inventory changes only when the approved company dispatch is confirmed or accepted quantities are recorded through distributor GRN. Secondary Orders are Activated after their lines are saved and may be invoiced and dispatched by the authenticated distributor without an order or dispatch approval step.

The Salesforce `ProcessInstance` record is the source of truth for Primary Order approval status. The order API returns `Not Submitted`, `Pending Approval`, `Approved`, `Rejected`, or `Recalled` separately from the operational `Order.Status`. Submission time, completion time, approver, and rejection comments are read from Salesforce approval history rather than copied into duplicate status fields. The DMS portal exposes `Submit for Approval` only for eligible Primary Draft orders with valid lines; the designated approver approves or rejects through Salesforce. Secondary order and dispatch APIs reject approval-submission actions. A Draft invoice cannot be cancelled while its order is pending approval.

Only `Order.DMS_Approver__c` is added to the business schema, as the related-user field required by the native approval step. `DMS_Order_Approval_Config__mdt` stores the designated approver's Salesforce username. The initially requested System Administrator approver policy was explicitly changed by the user to the selected active Standard User. The API requires the configured username to resolve to exactly one active Salesforce user, rejects self-approval, and refuses submission if configuration or a valid active approval process is missing. No profile or permission changes are made. `Order.DMS_Order_Approval` applies only to Draft Primary Orders with a DMS approver assigned; Secondary Orders are excluded by `Order.Type` and do not enter this process. No approval outcome is inferred from a successful HTTP response alone.
